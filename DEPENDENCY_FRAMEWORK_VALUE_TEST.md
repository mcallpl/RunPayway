# Dependency Framework: Ruthless Value Test
## Does It Create New Insight or Just Repackage Existing Data?

**Date**: June 17, 2026  
**Scope**: Test whether Dependency Framework adds genuine value beyond RP-2.0  
**Constraint**: Do not defend the framework. Try to kill it.  
**Assumption**: Every week building this is a week not spent on conversion, adoption, or other value.

---

# WHAT RP-2.0 ALREADY TELLS YOU

## Current RP-2.0 Outputs

```
income_persistence_pct          → How much income is predictable
largest_source_pct              → Concentration (biggest source as % of total)
source_diversity_count          → How many distinct sources
forward_secured_pct             → Income that's locked in/secured
labor_dependence_pct            → Labor vs. passive income split
earnings_variability_score      → Income volatility (0–1)
stability_band                  → Stability rating (A, B, C, D, F)
sub_band                        → Sub-classification within band
fragility_deduction             → Risk factors that reduce score
```

## What This Tells a Customer Already

**Example: Financial Advisor (W-2 $80k + AUM $40k + Commission $20k)**

RP-2.0 Output:
```
Largest source: 60%
Source diversity: 3 sources
Labor dependence: 60%
Earnings variability: 0.35 (moderate)
Stability band: B
Forward secured: 60% (W-2 portion)
Fragility: Concentration in employment; asset volatility
```

**What customer learns from RP-2.0 alone:**
- "My income has 3 sources; largest is 60%"
- "I'm 60% dependent on labor; 40% passive"
- "Income is moderate volatility"
- "Stability is B-band"
- "My employment income is secured; investments aren't"

# THE DEPENDENCY FRAMEWORK ADDS

## What Dependency Framework Would Tell

```
Primary Dependency: Employer (60%)
Secondary Dependencies: Asset (30%), Transaction (14%)

Dependency Composition: 60% employment, 30% asset, 14% transaction
```

**What customer learns ONLY from Dependency Framework:**
- "My primary risk is **employment** (not just 'biggest source')"
- "Secondary risks are **market** and **sales** performance"
- "I have a **layered income structure** (base + supplements)"

# PART 1: VALUE CREATED (NOT DUPLICATED)

## Where Dependency Framework Adds Genuinely New Insight

### #1: TYPE MATTERS FOR RISK PROFILE

**Example: Two customers, both 70% concentration**

Customer A: 70% from W-2 employment
- Risk: Job loss, company downsizing, industry collapse
- Mitigation: Credential portability, job market alternatives

Customer B: 70% from Upwork platform income
- Risk: Algorithm change, ranking loss, platform policy change
- Mitigation: Build direct client relationships, diversify platforms

**RP-2.0 says**: "Both are 70% concentrated."  
**Dependency Framework says**: "One is employment-dependent, one is platform-dependent. Different risk profiles."

**Value**: Transformational for risk conversation. Type changes mitigation strategy.

**Score**: 8/10 (genuinely new insight)

---

### #2: HIERARCHY CLARIFIES PRIORITY WHEN THERE ARE 3+ TYPES

**Example: Real estate investor (W-2 $100k + rentals $30k + flips $20k)**

RP-2.0 says:
- Largest source: 71%
- Labor dependence: 71%
- 3 sources
- (Doesn't clarify priority or structure)

Dependency Framework says:
- Primary: Employment (71%)
- Secondary: Asset (21%), Transaction (9%)
- **Tells you**: "Stable job base with real estate upside"

**Value**: Meaningful. Clarifies that employment is the foundation, real estate is supplemental.

**Score**: 7/10 (useful for multi-type clarity)

---

### #3: COMPOSITION FORCES CATEGORIZATION OF AMBIGUOUS CASES

**Example: Consultant with retainers ($50k) and projects ($50k)**

RP-2.0 says:
- 2 sources, both 50%
- (Doesn't clarify if they're same type or different)

Dependency Framework forces:
- Client-dependent (retainers, recurring)
- Transaction-dependent (projects, one-time)
- **Tells you**: "50% recurring, 50% volatile"

**Value**: Meaningful. Forces explicit classification that RP-2.0 leaves ambiguous.

**Score**: 7/10 (clarifies structure)

## Net New Value Summary

**Genuinely new insights Dependency Framework creates:**
1. Type matters for mitigation strategy (not just magnitude)
2. Hierarchy makes priority obvious for multi-type
3. Composition forces explicit categorization of ambiguous structures

**Estimate**: +15–20% additional clarity for multi-type customers (20% of population)

1. It's duplicating RP-2.0 data (70% overlap)

### The Honest Take

**If I were CEO:**

I would NOT build Dependency Framework now. Here's why:

1. **Low consumer ROI**: 80% of customers see redundant labels. 20% see marginal improvement. Average value: 3.2/10. Why spend 2-3 weeks on a feature that 80% of customers don't care about?

2. **No revenue path**: Dependency Framework doesn't generate revenue, reduce churn, or increase conversion. It's a nice-to-have feature on a free product. Advisors will use it if it's there, but won't pay for it. Institutions won't adopt it (it's not a standard).

3. **Opportunity cost is too high**: Those 2-3 weeks could:
   - Increase conversion by 15–25% (onboarding improvements)
   - Increase advisor engagement by 2–3x (advisor features)
   - Generate $100k+ annual revenue (enterprise API)
   - Any of these would dwarf the value of Dependency Framework

4. **Architectural elegance ≠ business value**: Dependency Framework is elegant. It's well-designed. It solves a real problem. But elegance doesn't pay the bills. Conversion, retention, and revenue do.

5. **Not a differentiator**: Competitors can build the same feature in 1–2 weeks. It's not proprietary. It won't help RunPayway win in the market.

6. **Maintenance burden**: Classification rules, edge cases, updates to RP-2.0 integration. This is ongoing tech debt for marginal value.

### The Business Case Against V1.5

**Return on Investment**:
- Cost: 2–3 weeks development + ongoing maintenance
- Benefit: 3.2/10 consumer value, 5/10 advisor value, 3/10 enterprise value
- ROI: Negative to barely break-even

**Opportunity Cost**:
- Same 2–3 weeks spent on conversion = +$50k–$200k annual revenue
- Same 2–3 weeks spent on enterprise API = +$100k–$1M annual revenue
- Same 2–3 weeks spent on advisor features = +$20k–$100k annual revenue

**Competitive Advantage**:
- Does Dependency Framework differentiate RunPayway? No. Competitors match in weeks.
- Does it lock in customers? No. It's a nice-to-have.
- Does it prevent churn? No. Customers stay for Decision Check™, not for framework elegance.

### When Dependency Framework Becomes Valuable

Dependency Framework **becomes** valuable when:

1. **Institutional adoption is real**: Fannie Mae, Freddie Mac, or major lender says "We want this data in your feed"
2. **Enterprise revenue is proven**: Credit bureau pays for enriched income data
3. **Advisor revenue is strong**: Advisors are paying for premium features; Dependency data becomes premium tier
4. **Conversion is no longer the bottleneck**: RunPayway has solved onboarding/conversion; now needs report-enhancement features

Today, none of those conditions are true.
